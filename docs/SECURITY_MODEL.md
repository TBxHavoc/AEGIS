# Security model

Permissions are ordered from read-only through local write, network, destructive, and privileged. The default policy is read-only, network-disabled, with an explicit built-in allowlist for bounded file reads/listing/search/hash, local knowledge search, read-only system diagnostics, bounded data calculations, and Python syntax parsing. File roots default to the knowledge root; code execution has no project root until configured. Network, MCP, local writes, and sandboxed test execution require explicit configuration and allowlisting. Sensitive HTTP tool calls require local access, a configured API bearer token, and explicit confirmation. Destructive confirmation does not bypass the tool allowlist; network tools additionally require `AEGIS_ALLOW_NETWORK=1`.

File tools use canonical approved roots, reject symlinks and protected project, credential, AEGIS database, audit, and security-component paths, cap file sizes, and use atomic writes with a one-time backup before replacement. Test execution uses bubblewrap on a credential-filtered read-only project snapshot with network isolation, where the host supports it. Web content and MCP results are untrusted; web URLs are restricted to public HTTPS destinations and page code is never run. UFW inspection is read-only; additive rule changes are separate proposals and require token-authenticated confirmation. Audit records are local, redacted and hash chained. Errors remain isolated tool/task failures. # Phase 8 additions

The implementation details, API configuration and current gaps are in [SECURITY_ARCHITECTURE.md](SECURITY_ARCHITECTURE.md) and [THREAT_MODEL.md](THREAT_MODEL.md). The new controls include safe mode, post-start source/audit/database checks, secret redaction, database health/consistent backup, UFW read-only inspection and additive approval-gated proposals, HTTP request bounds/rate limits/origin validation, and optional bearer authentication. UFW state could not be verified without root in the development environment; no host firewall changes were made. Encryption at rest, OS keyring, cookie sessions, persisted last-known-good releases and a transactional code activation/rollback workflow remain unimplemented.
